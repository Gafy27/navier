# Fuzz testing

Fuzzing is how you test the inputs your imagination doesn't produce. Parsers and
decoders — anything that eats bytes from outside — are the targets.

## Rules

1. **Fuzz what parses untrusted bytes.** File and message parsers, protocol
   decoders, decompressors, codecs.
2. **It finds reliability bugs too,** not just memory corruption: unhandled
   exceptions and panics that turn one malformed message into a denial of
   service, and inputs that blow the latency budget.
3. **Instrumented (coverage-guided) beats random.** The engine keeps inputs that
   reach new code and mutates them. Watch the coverage metric; a plateau means
   something is blocking the fuzzer, and it is worth finding out what.
4. **Feed it a seed corpus.** Real sample inputs — the ones already in your test
   fixtures — are the cheapest large coverage win. A dictionary of format
   keywords helps for structured formats.
5. **Drivers must be deterministic and cheap.** No RNG, no thread-timing
   dependence, no logging or disk I/O in the hot path. Slow drivers are weak
   fuzzers.
6. **Never crash on purpose in a fuzz target.** The engine cannot tell your
   deliberate abort from a real bug.
7. **Neutralize checksums and integrity checks** in fuzzer builds; the engine
   will otherwise never produce an accepted input. Gate that with a build flag.
8. **One driver, several knobs.** Split the generated bytes to select options
   rather than writing a target per configuration — splitting the input lets the
   engine correlate option and behaviour better than hashing does. Remember it
   makes existing seed files unusable without preprocessing.
9. **Continuous, not blocking.** Fuzzing runs indefinitely, so it can't gate a
   commit. Run it on a schedule, file what it finds, and promote every crashing
   input into a permanent regression test.
10. **Differential fuzzing compares two implementations** — feed both, report
    any difference as a crash. That is the tool for a migration where the new
    path must match the old one.
