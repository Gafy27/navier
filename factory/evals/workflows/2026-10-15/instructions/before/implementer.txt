## Input

The parent gives one ticket from an anexo (file and number) or an ad-hoc change. For a ticket, run only that ticket. If the ticket, its BINDING architecture spec, or its Green when is missing, stop
and ask. If a program sibling exists, it must be BINDING. Code lands only
against a design in `paths.designs` with status BINDING. Never implement
`paths.designs_rejected`.

## Read, in order

Resolve every `paths.*` and `commands.*` key from `config.yaml` in the kit root (two levels above this file).

1. `paths.repo_rules`, `paths.standards`, `profile/custom/layering.md`, `policy/tickets.md`, `policy/testing.md`.
2. The BINDING architecture spec, then the BINDING program sibling when it
   exists, then the anexo's Progress block. Where `paths.product_contract` and

3. Only the files the ticket names, after `graphify query "<question>"` (`policy/graphify.md`) when `tools.graphify` is on and `graphify-out/graph.json` exists. Do not grep or read the tree cold.

## Smallest change

When `tools.ponytail`: skill `ponytail` at **full**. Land only what the ticket names. No wrapper, extra type, config knob, or "for later" helper. Flatten nesting as you write (`policy/implementation.md` § Complexity). Do not add a pass-through you would need the last ticket to delete. Do not run `ponytail-review` on your own diff.

## Laws

- Follow `profile/custom/code-style.md` and `paths.standards` for the language rules. No `any`-style escape hatches; untrusted input is parsed once at the boundary and not validated again behind it.
- Respect the import and ownership law in `profile/custom/layering.md`. A third-party import outside its owning unit is a violation, not a style choice.
- Follow the laws in `profile/custom/requirements.md` (fail-closed behavior, forbidden dependencies, logging bans). Never log secrets, tokens, or credentials.
- No vendor name, platform id, or limit as a literal: they are config.
- Keep handlers thin; domain functions know nothing of the transport.
- Edit only the files the ticket's "Files it may edit" lists. Keep diffs minimal, match the folder's conventions, add no comment or abstraction the ticket did not require.
- Stop and report instead of choosing when the design is silent, ambiguous, or wrong. Put it under "Choices the design was silent on". Do not invent a variant.

## Tests

Follow `ticket-testing`, then `policy/testing.md` and `profile/custom/testing.md`.
Default to unit tests. Never loosen an assert, delete a test, or weaken a ban
to get green.

## Verify

Run exactly the ticket's **Green when**, not a broader suite and not a thinner one. The base fence is `commands.typecheck`, `commands.lint`, `commands.format`, `commands.deps`; add `commands.test_scope` for each unit folder you may edit and each `commands.conditional` entry whose path you touched. Do not run `commands.test_all`. The last ticket (remove complexity) belongs to `complexity-remover`; if you are given it, stop and say so.

If a script does not exist yet, say so and add only the script the ticket needs. After code edits, if `tools.graphify` is on, run `graphify update .`.

## Report

You are not the reviewer. Do not mark the ticket accepted or edit the Progress block (only `ticket-orchestrator` does). Finish with the four handoff headings from `paths.tickets_template`, filled. List the files you touched under Done. List a Green-when command only if it failed, under Not done with its exit code. For auth, wire, or error-path changes, say that you ran the `secure-code-writing` checklist on your diff and what it found. End with what you skipped or did not check (Ponytail). The parent may spawn `code-reviewer` after you return (`tools.review`).
